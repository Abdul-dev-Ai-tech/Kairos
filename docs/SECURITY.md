# Security implementation and operating notes

## Authentication and authorization

- Django authentication and server-side sessions, Argon2 password hashing in normal settings, 12-character minimum password validation, standard one-hour password-reset tokens. Tests deliberately use a faster hash to keep the suite small.
- Customer email is normalized and stored as the unique Django username, allowing email login without a custom auth database table. `create_admin` follows the same convention. When adding staff through Django's Users form, use their lowercase email as Username and also fill Email.
- Every admin URL uses `AdminSiteOTPRequired`; the custom dashboard and admin order receipt are protected by the same admin wrapper. Password-only customer login does not grant staff dashboard access. Staff must complete a maintained `django-two-factor-auth` TOTP challenge. Recovery codes use `django-otp`'s single-use static tokens. No OTP recovery bypass web endpoint is provided.
- Owner is a superuser. Store Staff has scoped catalogue/order permissions; Payment Verifier grants payment verification only. Neither role grants user/permission administration or store identity settings. Payment verification checks permission, staff status and verified OTP in the service as well as in admin.
- Account order history is filtered by owner. Order detail and receipt enforce ownership and return 404 to strangers. Guest confirmation requires the originating session or a signed, order-scoped link lasting seven days. A UUID alone is insufficient. Signed guest links are bearer secrets; do not publish or log full links.
- Axes stores failed login attempts in the database and blocks after five failures, with a 20-minute cooldown, keyed by IP and username+IP. TOTP devices also apply their package's token throttling. This is not a full DDoS or bot-abuse defence.

## Requests and output

All mutating storefront actions are POST forms with CSRF protection. Server forms validate prices/quantities, emails, choices, delivery and account fields. Untrusted strings are escaped by Django templates. Plain-text policy/product descriptions cannot inject HTML. Product JSON-LD and variant JSON are escaped for script contexts; no invented ratings or authenticity schema is emitted.

Session cookies are HttpOnly/SameSite=Lax, and production adds Secure to session and CSRF cookies. Production enforces HTTPS redirect, HSTS, nosniff and frame denial. Security headers include referrer and permissions policies. The current CSP permits inline scripts/styles because Django admin and third-party OTP templates use them; it is not a strict nonce-based CSP. No external analytics or advertising scripts are included. Do not claim CSP alone prevents XSS.

Only safe local return URLs are accepted after cart/wishlist actions; Django validates authentication next redirects. Filter queries use ORM expressions. CSV cells beginning with formula/control prefixes are quoted for spreadsheet safety. `DATABASE_URL`, email passwords and signing keys come from environment values.

## Commerce consistency

Checkout runs in a database transaction and locks the cart, relevant products/variants, selected shipping/payment rows and coupon. Prices and discounts use Decimal, with half-up rounding for coupon currency. A conditional stock decrement is a second guard against unavailable quantities. Cart prices and any client-supplied amount are not trusted. Coupon expiry, limits, minimum, zone coverage, method activation and product availability are rechecked.

A unique checkout UUID tied to the source cart makes a duplicate form submission return its original order. Order items snapshot purchased names, finish, SKU, quantity and price. Payment instructions and totals are snapshots. Order/customer/amount snapshots are read-only in admin. Product admin POSTs lock the product before saving variants and reject stale stock snapshots; editing unrelated product details cannot silently put sold inventory back. Coupon admin writes preserve the current redemption counter. State transitions are validated by the service; cancellation locks/replenishes stock once. Paid status requires an OTP-verified authorized actor. Order changes and business admin writes create audit entries; Django's own admin log also records model operations.

PostgreSQL locking semantics need the included PostgreSQL race tests on the target environment. SQLite checks do not prove concurrent checkout behaviour. See VERIFICATION.md.

## Uploads and storage

Only JPG, PNG and WebP inputs are accepted. Extension, decoded format, pixel count/dimensions and a 5 MB limit are checked. Files are decoded/re-encoded to WebP (PNG for logos/favicons), with random UUID filenames and no camera metadata. Product images get 480/960/1600px versions. SVG uploads, arbitrary HTML and executable files are rejected. Uploaded file URLs are generated by Django storage; no arbitrary filename paths are trusted.

Nginx's example limits entire requests to 25 MB; if uploading many full-size images at once, reduce sizes or upload in batches. Media must be persistent and never served by an executable handler. Replaced/removed images are not automatically purged from storage, so historical files may remain until an owner-controlled retention job removes unreferenced files after backup. Plan data retention, access and erasure procedures for customer and audit records.

## Proxy and incident operations

By default, Axes uses the peer address. If all traffic arrives through a reverse proxy, this can group users under that proxy IP. Before launch, configure a trusted client-IP extractor only when the proxy strips incoming headers and the backend cannot be reached directly. The optional `core.security.client_ip` callable included here accepts `X-Real-IP` only with `TRUST_PROXY_HEADERS=true`; the supplied Nginx example overwrites that header. Review this against your actual hosting topology.

To inspect/recover a legitimate login lockout, use `python manage.py axes_list` if supported by the installed package or inspect Axes access attempts in owner admin. `python manage.py axes_reset` clears failed-attempt records; use only as an owner-operated recovery step after understanding the incident. This does not disable OTP. If the owner loses the authenticator and all backup codes, recovery requires trusted server administration and explicit identity verification outside the web application; do not create a public reset-OTP endpoint.

Keep dependencies patched, secrets backed up securely, and old/departing staff accounts disabled. Back up PostgreSQL and media, encrypt/access-control backups, and test restore procedures. An application administrator can intentionally change prices, stock or shipping; this is part of that authorized role. Production infrastructure, email delivery, access controls at your host and independent security review remain deployment responsibilities. No security certification, vulnerability-free guarantee or penetration-test claim is made.


## Order-location and notification update

Lahore city/area, optional safe map host and paired service-bound coordinates are
validated in forms and the checkout service. Browser geolocation is permitted only
on same-origin checkout pages and is requested only on button press. Coordinates
are not proof of an address/city boundary. Consent/timestamp/text version and ETA
are order snapshots. Staff and customer order checks still protect their data.

Meta credentials are server environment variables. Outbox rows are unique by
order/kind; unknown network outcomes require review. HTTP redirects are disabled
for the authenticated Meta send request. Webhooks use constant-time HMAC/verify-
token checks; public retry endpoints require a separate bearer secret. Owner retry
actions require a verified superuser. Provider errors retain codes, not tokens or
full payloads. No real WhatsApp/SMTP/cloud credentials or production data were tested.
